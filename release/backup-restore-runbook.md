# 工作台备份与恢复

适用构建：本地源码 0.1.0、备份格式 1、已知 SQLite schema 1–4。当前工程验证使用假外部模型响应，数据、文件渲染、数据库、配对检查和恢复引擎均为产品实现；本手册不代表签名安装包或旧版可执行程序已获验证。

## 用户操作

1. 在任务详情确认所有运行任务已暂停或结束；仍有工作租约、运行中远程请求或待核对取消的任务时，备份会拒绝。恢复还要求没有待调度任务。
2. 打开“设置 → 本地存储 → 备份与恢复”，点击“创建并保存备份”。由系统文件对话框选择 ZIP 保存位置；选择新文件名，已有文件不会被覆盖。
3. 等待页面显示实际核验文件数。备份包含一致性 SQLite 快照、数据库引用的不可变文件、原件及译文、发布包 manifest、持久任务工作区及证据、非秘密设置、schema 与应用版本。SQLite WAL 中已提交数据通过 SQLite backup 接口进入快照。
4. 用户会话、附件和成果是私有内容。备份保存在本机所选目录；程序不会上传或发送。连接凭证、系统账户文件、根目录缓存与派生翻译缓存不进入备份。
5. 恢复时点击“选择备份并恢复”，选择工作台 ZIP。程序先在本机暂存目录检验路径、文件集合、每份 SHA-256、SQLite 完整性、外键、已知 schema SQL、所有引用及双语格式/版本配对。
6. 系统确认框显示核验文件数与 schema；确认“恢复并重新连接”后，程序在当前数据目录的同级新目录恢复、迁移并重建 SQLite 索引。只有整体验证完成才重启托管服务、保存新目录选择。
7. 当前数据目录始终保留。完成页面显示实际恢复结果，随后到连接设置重新核验模型连接。凭证没有随备份恢复，页面不能凭旧数据库记录宣称已登录。
8. 若保存、校验、恢复、迁移或重启失败，遵循显示的中文错误；原目录仍保留。不要手动删除它或强制修改已冻结的数据库。重启应用后，再选一份已知完整备份重试。

## 文件边界与限制

- 桌面 renderer 只能发起白名单 `storage.backup.create` / `storage.backup.restore` 空参数调用。路径来自主进程系统对话框，HTTP 导入使用字节与临时授权 ID；renderer 不能提交任意磁盘路径。
- 备份格式 1 最大 256 MiB、20,000 个数据文件；ZIP 上传、解压总量和导出大小均受限。大于此范围的工作库需要后续流式备份扩展；失败时不会替换活跃数据。
- ZIP 路径中的绝对路径、盘符、`..`、反斜杠、控制字符、设备名、尾随点/空格、重复大小写路径、符号链接与特殊文件会被拒绝。磁盘目录中的链接、junction/reparse 与备份文件硬链接同样拒绝。
- 备份不是通用 ZIP 导入器。只允许数据库、引用 blobs、任务工作区和证据的受管相对路径；额外凭证文件或未知根目录文件导致拒绝。
- 服务为一次桌面选择保留不透明备份 ID，重启后需重新选择 ZIP。内部已验证备份暂存副本位于当前数据目录的同级 `.目录名-backups`；当前工程没有自动删除或轮替用户备份的机制。
- 已知 schema 1–4 的历史备份可经现有事务迁移升级。未来 schema、改过迁移历史、额外触发器或 schema 对象不接受。任务工作区写租约和锁文件不会恢复。
- 系统管理的连接凭证不会进入备份。用户主动放进正文、附件或成果中的秘密属于用户内容，备份按原字节保留；此流程不会破坏原件来自动脱敏。

## 隔离演练与证据

使用默认解释器，在源码根目录执行：

```powershell
& services/orchestrator/.venv/Scripts/python.exe -m pytest tests/storage tests/integration/test_storage.py tests/integration/test_storage_settings.py tests/integration/test_storage_relocation.py tests/integration/test_phase_two_migration.py -q
npx vitest run tests/desktop
npm run typecheck:desktop
```

`tests/storage/test_backup_scenario.py` 的 six cases 生成真实产品双语 Markdown/PDF、两代原件、旧版历史包与暂停任务。测试将实际持久记录装入已知 v3 schema，再执行备份和 v4 恢复；这是前一 schema 的真实数据样本构造，不是发布过的 v3 可执行程序。每次执行的 `restore-report.json` 记录恢复哈希、原哈希、体积、用时、schema、凭证状态和原目录保留结果。

故障演练包括缺中文文件、坏数据库、坏哈希、空间不足、文件级 manifest 重新计算后仍错误的原文/译文配对、删除任务原件及 source manifest 后重算外层 manifest、改写原件及两层哈希但与数据库合同/规划/材料等源哈希冲突、复制失败、Windows junction、ZIP link 与每个 schema 4 SQL 步骤、schema 历史提交和最终 COMMIT 故障。失败结果必须为拒绝，当前数据库逻辑记录与当前文件哈希不变。

## 匹配旧 schema 回滚

1. 用升级前已核验备份保持独立旧目录，确认备份 manifest 的 schema 与旧程序支持范围匹配。
2. 当前恢复入口会升级到当前已知 schema，因此不要把恢复后的 v4 目录交给仅支持 v3 的旧程序。旧程序直接调用现有迁移入口会收到 `NEWER_SCHEMA`，不会改写数据。
3. 签名旧程序的实际回滚应由发布运行手册在隔离环境执行，选用原保留目录或匹配 schema 的原备份。本文仅留本地引擎与 schema 拒绝测试证据，不授权切换安装包或实际发布。
