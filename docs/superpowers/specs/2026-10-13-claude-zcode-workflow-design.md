# Claude Code 与 ZCode 综合任务协作设计

日期：2026-10-13（Asia/Shanghai）  
阶段：工作流设计稿，供后续开发使用。程序尚未实现，用户本机的接入能力尚未验证。

新增要求已形成[工业化开发计划](../plans/2026-10-13-industrial-agent-workbench-plan.md)、[界面规范](../../../DESIGN.md)及[条件翻译与双语交付规格](2026-10-13-translation-delivery-spec.md)。以下基础工作流结合这些细化执行；语言、界面和原文来源以新规格为准。

最新约束：Claude 路径由 B 完整完成中文输入到英文的翻译，以及 A 英文定稿到中文的翻译；GPT 不启用强制翻译。主聊天只呈现问题、最终回答与文件。Claude 文档交付 A 实际输出的完整英文原件和 B 中文译文，必要的 A 定稿输出成本计入预算。A 查看经校验的英文材料视图及必要原件定位，保留原始证据和对应关系。

## 1. 已确认的目标与工具

- 支持编程开发、论文、普通文档，以及包含数据分析、图表和上述交付物的综合任务。
- A 主要使用 Claude Code 中的 Claude，负责方向、关键判断和最终验收；保留 GPT 替换 A 的接口。
- B 使用用户现有 ZCode 中的 GLM，负责执行、自检、修复和交付文件制作。
- 质量目标是保持 A 单独完成同类任务时的智能表现与交付水平；在此条件下尽量减少 A 的总 token 消耗。不能仅以满足基础验收项代替这一质量目标。
- B 优先完成质量，同时设置可调整的运行上限。
- 当前先确定工作流。具体 Claude/GLM 版本、ZCode 安装版本、GPT 入口及各类文件工具由后续接入检测确认。

用户优先级为：A 级质量目标 → 尽量减少 A 总 token → 在前两项允许的范围内优化耗时和 B 用量。

优化目标是在代表性任务上达到 A 独立执行的质量基准，再降低每个合格交付的 A 用量。具体效果用真实任务测量，不预设固定节省比例。当前不能保证所有任务都同时达到同等质量与明显节省；对主要成本就是高难推理本身的任务，A 可能仍需投入接近独立完成时的工作量。

## 1.1 保留 A 的关键推理

设计重点是让 A 的关键判断驱动 B 的大量执行。A 的职责不能退化为只在开头写提示词、结尾读摘要。

| 工作性质 | 默认责任 |
| --- | --- |
| 定义真正的问题、识别遗漏约束、选择目标和方法 | A |
| 关键架构、算法思路、研究假设、论证结构与取舍 | A |
| 检索、摘录、建立材料索引、运行工具、批量加工 | B |
| 按已确认方案写代码、展开正文、制作图表和排版 | B |
| 可由明确证据判定的检查与修复 | C 运行检查，B 修复 |
| 判断证据是否充分、结果是否合理、方向是否需要调整 | A |

A 在任务书中标明决定质量的关键判断及其依据、验证办法和升级条件。B 在约定范围内作局部决定；出现影响架构、方法或结论的新证据时，将必要原件和具体问题提交 A。

这些记录是可审核的决策摘要，不要求输出模型的完整内部思考过程。A 独立查看用户目标和关键依据，避免只能从 B 已筛选的材料中作选择。

## 2. 总体结构

系统由 A、B 和普通调度程序 C 组成。C 不使用第三个模型承担常规调度。

| 组件 | 职责 | 输出 |
| --- | --- | --- |
| A：指导与验收 | 关键推理、目标与方法选择、方案取舍、困难问题和最终结论 | 任务书、关键决策、缺陷清单、验收结果 |
| B：执行与修复 | 整理材料、细化步骤、执行、检查、修复、制作交付包 | 成果、证据索引、执行摘要、已知缺口 |
| C：调度程序 | 状态管理、启动执行器、文件交接、程序检查、预算、重试和版本管理 | 任务记录、验证结果、状态面板和最终包 |
| 适配器 | 连接 Claude Code、ZCode 和未来的 GPT 入口 | 统一任务请求与执行事件 |
| 验证器 | 按任务类型运行可重复的检查 | 绑定成果版本的检查记录 |

A 与 B 通过明确的任务文件和成果版本协作，不依赖共享聊天记录。任务状态以 C 的持久记录为准；B 的报告不能直接改写任务目标、验收标准或最终通过状态。

## 3. 一条通用流程，四类验收配置

所有任务使用相同的状态和交接协议。程序按用户选择、已有模板或 B 提供的分类建议选取配置；语义不明确时由 A 在制定任务书时确认。C 不通过简单关键词自行作重要业务判断。

| 类型 | B 的主要工作 | 程序验证 | A 的主要验收 |
| --- | --- | --- | --- |
| 编程 | 实现、调试、运行、编写必要测试和使用说明 | 构建、关键测试、接口结果、文件和依赖检查 | 需求覆盖、设计合理性、关键逻辑和异常行为 |
| 论文 | 材料整理、检索与引文整理、分析、图表、草稿和修订 | 引用与编号完整性、统计复算、数据和图表关联、导出检查 | 研究问题、贡献、论证、证据支持、方法与结论一致性 |
| 普通文档 | 报告、方案、说明书、演示稿等内容与排版 | 必备内容、数字和名称一致性、目录、文件可打开与导出 | 受众匹配、信息准确、结构、清晰度及可执行性 |
| 综合任务 | 按依赖关系制作多种成果并整合 | 子任务验证、跨文件引用和版本一致性 | 整体目标、跨成果逻辑、最终包完整性 |

规则检查只能覆盖可机械判断的项目。例如引用条目存在，不代表来源支持该论点；测试通过，不代表所有需求均已满足。语义性标准需要 A 审查，必要时补充外部证据。

论文和研究任务不得补造文献、实验结果或数据。未能访问或核实的资料标记为未验证；若相关内容是必需证据，则进入受阻状态，不能把它当作已完成。

## 4. 标准执行过程

### 4.1 接收与整理

1. C 保存客户原始需求和附件，记录交付格式、完成条件及已有资源。
2. 材料较多时，B 建立材料索引、提取候选需求和缺口，并标注原文、页码或文件位置。
3. A 阅读原始需求、整理结果及必要原件；影响目标、方法或交付的缺失信息需澄清。低影响细节采用显式记录的默认值。

### 4.2 A 制定任务书

A 输出足够明确但尽量精简的任务书，并承担决定结果的关键推理。固定格式由模板提供，不要求 A 每次重新撰写通用规则。精简报告不等于强迫 A 缩短必要推理或在信息不足时作结论。

任务书至少包括：任务编号与版本、目标、类型、输入索引、交付物、约束、关键方案、关键判断与依据、子任务依赖、验收项、B 自主范围、升级条件和运行预算。

每条验收项有独立编号，声明是否强制、如何验证、证据形式及负责验收者。质量要求使用可解释条件，避免只有“尽可能好”或模型自评分数。

### 4.3 B 执行

B 细化操作步骤，读取必要资料，在任务工作区完成成果并保存检查点。普通进度和完整工具日志由 C 存储，不逐条交给 A。

B 可以切换执行、自查、整合三种工作阶段；这些阶段不等于拥有三个独立可靠的审核者。同一模型自查只是质量控制的一部分。

长任务在约定里程碑提交状态；常规文件编辑和检查不需要反复唤醒 A。B 发现原方案的重要前提不成立、关键结果异常或存在影响结论的替代解释时，应触发 A 的判断，不等到最终验收才暴露。

### 4.4 验证与自主修复

C 对成果的固定版本运行约定验证器，记录实际命令或检查方式、结果、时间、环境摘要和证据位置。

明确失败的检查交给 B 修复；修复后重跑受影响项目。没有验证器的语义项目进入待 A 审查状态，不默认通过。

通信重试与质量返工分别计数。任务结束、进程退出或出现“完成”字样，都不直接代表成果通过验收。

### 4.5 提交验收包

B 提交短摘要、成果清单、逐项需求映射、证据索引、变更摘要、已知问题与未验证事项。C 加入实际验证结果并生成本次成果快照。

A 默认先读取这个包，再按验收需求打开原件、代码差异、关键来源、图表或页面预览。摘要用于定位，不能替代实际证据。

### 4.6 A 验收

A 的结果采用四种明确决定：

- PASS：强制标准通过，可以交付本次版本。
- REPAIR：存在缺陷，逐项说明位置、影响、修复要求与通过条件。
- NEED_EVIDENCE：结论所需材料不足，补充证据后再判断。
- BLOCKED：缺少必要输入、访问条件，或当前方案/能力无法完成，明确下一项必要动作。

返修时 A 主要输出缺陷清单。B 提交修改与影响范围，程序复验，A 再审查相关部分。修改影响架构、结论或整体逻辑时，扩大复核范围。

### 4.7 交付

B 在最终验收前准备说明文件和交付包。A 一并检查；C 将验收结果绑定成果版本，并向用户呈现批准的文件和说明。

批准后的实质变更需要相应复验。向外部客户发送、发布或部署属于单独动作，按任务中已有授权执行。

## 5. 综合任务按依赖关系推进

示例：客户要求“分析一份数据，形成研究报告，并提供可复现代码”。

执行链为：

原始数据核对 → 清理与分析代码 → 分析结果 → 图表 → 论文或报告 → 可复现交付包。

独立步骤可并行；依赖上游的步骤等待上游满足条件。第一版默认一个 B 执行队列，避免多个执行会话修改同一份文件；后续并行使用独立工作区和明确合并点。

每个下游成果记录所依赖的上游版本。数据、计算方法或关键代码改变后，相关图表、文字结论和验收记录标记为需要复验，并沿依赖关系传播。

对复杂研究或大型开发任务，A 在高返工成本的位置安排必要里程碑，例如分析方法确认、核心架构验证、关键结果解释或论文提纲确认。里程碑数量由依赖、证据和难度决定，不固定为一个。不得为了减少参与次数而跳过必要判断。

## 6. A 的 token 管理

简单且方向明确的任务可以只让 A 参与“制定任务书”和“最终验收”两个阶段。复杂任务按关键判断触发 A；两阶段是简单路径，不是全局调用上限。阶段数不是底层模型请求数；Claude Code 的工具使用、读取和推理仍计入实际消耗。

采用按任务调整的三种执行深度：

- 常规执行：A 确认方向，B 完成大部分执行，A 验收。
- 关键节点指导：A 处理方法、架构或结果解释等节点，B 在节点之间执行。
- A 主导困难部分：A 直接承担核心推导、难点设计或关键论证，B 负责材料、运行、展开与交付制作。

执行深度可以升级。若节省 A 用量将使质量低于基准，则增加 A 的必要投入，或如实记录当前资源下无法完成；不能悄悄降低标准。预算耗尽时仍按停止规则保存状态。

### 默认上下文

- 规划阶段：客户原始需求、相关约束、必要材料索引和关键原件。
- 验收阶段：任务书、当前成果版本、需求映射、实际检查结果、已知问题和必要成果。
- 返修阶段：尚未关闭的缺陷、当前变更、受影响上下文与复验结果。

### 节省方式

1. 通用角色规则和任务模板复用，避免 A 重复生成。
2. 长日志、搜索过程和失败尝试保存在任务目录；A 按需提取。
3. 使用文件索引与差异定位，再读取理解问题所必需的上下文。
4. B 负责格式化、完整成稿和打包；A 不必再抄写一遍批准的成果。
5. 同类重复任务复用已批准任务书，目标和条件变化时由 A 重新确认。
6. 控制无关历史，保留已确认决定、约束、来源及未解决事项。
7. 适配器支持时利用缓存；缓存用量和实际成本分别记录，不能把缓存视为零 token。

文件读取仍消耗输入 token，保存到文件本身并不带来免费上下文。短报告限制是可调整软限制，不能截掉关键风险或未验证事项。

### 验收深度

- 简单、可机械验证任务：A 阅读成果关键部分和实际验证结果。
- 复杂任务：A 检查核心路径、主要结论、例外和跨文件关系，并按需要扩大阅读。
- 明确要求完整审稿的论文：A 分节阅读全文，结合图表、方法、证据检查跨节逻辑；对应 token 成本是质量要求的一部分。
- 若采用抽样检查，记录范围与局限；样本由任务规则、C 或 A 选择，不能全部由 B 挑选。

不以 B 的自信程度或自行宣布完成作为降低审核深度的理由。A 的读取、推理或复核不能单纯为了达到节省比例而被截断；优先消除重复生成、重复阅读、机械操作和无效返工。

## 7. 修复、升级与停止

以下为首轮试运行的可调整默认值，不代表经过实测的最优参数：

| 条件 | 动作 |
| --- | --- |
| 明确的格式、构建、计算或测试失败 | B 自主修复 |
| 同一问题连续两轮无实质进展 | 提交 A 判断 |
| 一轮执行内自主质量修复达到三轮 | 汇总证据，进入 A 诊断 |
| 经 A 指导返修两轮仍有关键缺陷 | A 改变方案、拆小任务或接管困难部分；再次执行需新的有界计划 |
| 缺少关键资料、需求冲突或超出约定范围 | 保存进度，提交必要问题 |
| 网络超时或服务限流 | C 按适配器规则退避重试；先核实上一请求状态，防止重复执行 |
| 凭证失效、人工交互需求或权限不足 | 保存进度并呈现具体阻塞 |
| 到达时限或资源上限 | 保存检查点和未完成项，停止继续消耗，不能自动标记通过 |

A 接管局部问题时，先保存版本并移交写入责任，完成后再让 B 继续，避免同时修改。

## 8. 任务状态与恢复

主状态：RECEIVED → PLANNING → EXECUTING → VALIDATING → REVIEWING → APPROVED → DELIVERED。

分支状态：NEEDS_INPUT、REPAIRING、BLOCKED、PAUSED、FAILED、CANCELLED。补充证据回到执行和验证；修复也必须经过验证再进入复核。

C 是状态的唯一写入者。每次请求携带 task_id、attempt_id 和相关版本，记录外部会话/执行编号。延迟到达的旧结果不能覆盖新版本状态。

启动和结束事件持久化。进程中断后，先确认外部执行是否仍在进行，再决定继续、接收结果或重试。检查点文件完成写入后再发布相应事件，避免读取半成品。

用户修改需求时增加任务书版本，识别受影响工作，不能把旧要求下的 PASS 沿用为新要求下的通过。

## 9. 对接与工作区设计

### Claude Code 适配器

使用其受支持的程序化入口和结构化结果。启动、恢复、错误和用量事件通过适配器转成统一格式。需要本机验证版本、登录方式和所需工具能力。

### ZCode 适配器

保留用户现有 ZCode + GLM 组合。官方仓库存在 Agent CLI 与非交互相关入口，后续根据已安装版本验证可用方式。

首个接入实验只验证：接收任务文件、在指定工作区处理一个小任务、输出结果、识别完成和失败、恢复执行以及正确选用 GLM。

命令行执行与桌面任务是否共享会话、是否在桌面可见，必须单独验证；不能由共享项目文件推断。账号可用额度也按实际入口确认。

若现有版本没有合适的自动入口，先保留相同文件协议并由用户在 ZCode 手动触发；界面自动操作作为后续备选，需要另行验证稳定性。不得把未验证的接入方式描述为已全自动运行。

### GPT 适配器

沿用 A 的任务书与验收结果协议。具体入口待用户选定后实现。每个任务默认使用一个 A；替换模型时传入必要状态，新模型仍需完成实际验收。

### 文件组织

建议每个任务具备以下逻辑区域：原始输入、任务书、B 的工作区、成果快照、验证证据、A 的评审和交付包。

A 主要写任务书与评审，B 写成果和执行报告，C 写状态和程序验证记录。运行日志与凭证不作为默认交接内容；跨任务只复用通用模板和明确允许复用的材料。

## 10. 程序实现边界

第一版建议使用 Python 实现 C，SQLite 保存状态，文件目录保存成果；代码任务使用 Git 或文件快照记录版本。

模块包括：任务入口、状态调度、Claude Code 适配器、ZCode 适配器、交接包生成、验证器注册、版本与依赖管理、用量统计。

文件处理与验证工具通过能力检测注册。例如 PDF、Word、LaTeX、表格和图表各自需要能实际读取、生成、渲染或检查的工具。声明支持某类任务前，必须确认相关工具可用；模型能生成文本不等于能正确交付所有文件格式。

首版提供聊天式图形界面、条件翻译及文档交付。主聊天保持问题与最终答案，连接、用量和必要诊断放在独立页面；完整状态留在后台。GPT 路由与无强制翻译分支纳入工业化版本验收，多 B 并行后续扩展。

## 11. 验收与效果评估

程序本身至少通过以下场景：

1. 编程任务从需求到实际运行、验收和交付。
2. 文档或论文任务按原始材料生成成果并核实关键依据。
3. 数据分析、图表与正文混合任务保持版本一致。
4. B 报告完成但成果缺失或验证失败，系统正确退回。
5. A 提出缺陷后，B 定点修复并完成复验。
6. 中断、重复通知和延迟结果不会产生重复执行或错误交付。
7. 上游成果改变后，相关下游成果和批准状态需要复验。
8. 无法完成或资源耗尽时保存进度并呈现真实状态。

用一批有代表性的任务比较 A 单独执行与本工作流。保持需求、可用资料、必要工具和质量标准可比，记录模型、工具版本、任务难度与各自资源投入。评价正确性、完整性、关键推理、事实与证据、表达及最终可用性；尽可能隐藏产出来源进行人工或独立评测。

A 自己说“与我单独完成一样好”不能作为等效证据。检查真实成果、可执行验证和领域评审结果，并记录误差、样本范围和质量差异。试运行观察到相当质量仅支持所测任务范围，不能外推保证所有任务。

基准比较在设计验证和定期抽样阶段进行，不要求每个正式任务都额外完整运行一次 A。保留未用于调整工作流的任务作独立验证，按领域和难度分别报告。针对质量下降的任务类型提高 A 参与程度后再评测。

核心指标：最终质量、交付后缺陷、首次验收通过率、返工次数、总耗时、B 用量，以及“A 在所有任务和尝试中的总 token / 最终合格交付数量”。分任务类型报告，避免总体均值掩盖论文或代码任务的差异。

分别记录输入、输出及服务报告的缓存/推理用量类别，遵循提供方计量口径避免重复计算。请求级记录去重；会话累计数不能逐轮相加。无法取得真实用量时明确标注估算值。
