# SQLite 与不可变 blob 的备份边界

D008 的恢复单位是同一个时间点的 SQLite 元数据、全部被 artifact_revisions 引用的 SHA256 blob，以及该版本的迁移 SQL。仅保存 SQLite 文件或仅保存文件名无法恢复成果来源与依赖。默认 SQLite 数据库使用 WAL、foreign_keys=ON、synchronous=FULL；服务以 BEGIN IMMEDIATE 串行登记写入，不在多个线程共享连接。

备份操作应先暂停新登记并等待现有写事务结束，再用 SQLite backup API 取得一致快照，并按该快照列出的 byte_sha256 复制原件。为快照与 blob 集合保存哈希清单、schema_version 历史和软件版本。活动数据库的 WAL 不能在仍有连接时被任意删除；直接复制一个活动主数据库文件不能代替一致快照。这个步骤属于后续发布/备份功能，D008 只定义边界。

恢复时先在独立目录核对快照完整性、foreign_key_check、支持的迁移版本、每个引用的文件存在性及实际字节哈希，全部通过后再切换工作目录。未知新 schema、迁移 SQL 哈希改变、丢失或损坏 blob 应停止恢复并保留证据，不通过删约束、改哈希或重写原件继续运行。迁移失败会整体回滚所有待应用版本和 schema_version，不丢弃旧数据。

登记顺序是临时文件写完、flush/fsync、原子 hard-link 到哈希路径且禁止替换，再插入数据库，最后提交。登记前持有数据库写锁，所以锁超时不会启动文件写入。文件失败不会产生可见成果行；数据库失败或进程退出可能留下完整但未被引用的 blob，它不能作为发布成功证据。临时文件和未引用 blob 的清理需要对照一致快照，不能盲删哈希目录。

D008 已验证真实 SQLite 锁、真实进程退出、并发创建原件、迁移回滚与缺失/坏哈希；ENOSPC/EIO 是在真实文件操作边界注入的故障。硬件断电和完整产品备份恢复由后续发布验收接续。Windows 上文件内容先 fsync，目录元数据的断电持久性未单独验证。
