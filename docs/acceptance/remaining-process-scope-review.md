## Findings

1. **HIGH — Changing step_id bypasses the durable unknown-remote guard after normal exit or owner death.** `services/orchestrator/app/runtime/leases.py:54` only matches unknown remote records whose local state is cancelled/failed/resource_limit; `processes.py:227` treats that predicate as the admission gate for a new step. A normal native fixture exit recorded exited/unknown, and B.retry launched for the same task/attempt without external reconciliation. A second actual service process exited 84; Windows Job close correctly killed its worker, but the persisted row remained running/unknown. A reopened manager also admitted B.retry. The distinction between local death and unknown remote completion is otherwise correctly recorded, but the step key creates a new-start escape. Deny new execution for every unresolved prior remote invocation, including running/exited rows, until trusted explicit reconciliation confirms it. Retain the old association and keep legitimate independent steps available after that confirmation.

2. **MEDIUM — A monitor error leaves its owned temporary directory and a running ledger row while resource_snapshot reports zero.** `services/orchestrator/app/runtime/processes.py:406` closes Job/event/process handles after an exception, then `:413` removes the handle from active tracking without the normal temporary-directory cleanup at `:397` or a failed ledger result. With an injected QueryInformation error at the actual monitor boundary, wait correctly raised PROCESS_CLEANUP_FAILED and the real worker was dead, but the directory still existed, the lease remained running, and resource_snapshot reported temp_dirs=0. close then had no tracked handle to clean. Complete bounded cleanup of owned readers/native handles/temp state on this branch, record explicit failure, and retain/account any resource that cannot be safely reclaimed. Otherwise repeated monitor failures evade the advertised temporary-directory budget.

3. **MEDIUM — The registered English proof is shallowly frozen and can change its protected spans after registration.** `services/orchestrator/app/runtime/context_gateway.py:28` is a frozen dataclass, but `:39` only annotates protected_spans as a tuple; a list is accepted and `:55` keeps the same proof object in the registration mapping. A registered proof initially rejected Chinese natural language. Appending one ProtectedSpan to the original list, with no new validation id and unchanged source/view hash, caused `:89` to exempt the whole source and return the original Chinese bytes as language=en. Deep-freeze/copy protected spans and validate every span record when constructing or registering the service proof; mutation must not change previously granted read authority. This reproduces reference-authority mutation, not an assertion that this gate certifies translation semantics. Real Claude execution remains disabled without its later language/quality dependencies.
