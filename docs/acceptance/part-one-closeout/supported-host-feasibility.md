# Supported host feasibility — read-only findings

Checked on 2026-10-14. This investigation made no provider/model/API calls, did not launch a host, build or install dependencies, open authentication UI, read account/configuration files, obtain credential values, copy a credential store, or alter settings. Public source files were cached under the ignored `.tools/supported-host-feasibility/` directory. The only OpenAI credential observation was `Test-Path Env:OPENAI_API_KEY`, which returned **false** in the current process environment; its value was not read. This does not establish the state of every environment or credential store on the computer.

The answer is **conditional source-level feasibility, with no verified installed SDK connection**. ZCode's official repository contains Node account-service factories and a real Start Plan registry/authentication path. It is inaccurate to call all account handling Electron-only private IPC. The installed desktop host bundle, however, is not an externally importable account SDK, and the source factories are private workspace packages. A fixed-source Node integration is a possible implementation lane; this read-only result does not remove `HOST_ACCOUNT_CONTEXT_REQUIRED`, verify current entitlement, or complete the production runtime.

## Minimum source composition and its unresolved runtime boundaries

The smallest plausible composition uses the fixed official workspace source and its original build toolchain, with narrow service imports instead of importing the desktop bundle. The official server's build already bundles workspace services for Node. A local build is supported by the repository, but neither this smaller composition nor the official server build was run by this investigation. Source-level imports and a successful build alone would not prove API authorization or compatibility with the installed production security edition. [Official server build](https://github.com/zai-org/ZCode/blob/aac4755666d09fdcd70272fcf063c077a639015f/packages/server/tsup.config.ts).

1. Keep credential handling inside the official `createCredentialService()` and `OAuthCredentialRepo` implementation. The service resolves its existing store internally; the external controller must receive only booleans/fixed reason codes, never token values, decrypted records or user identities. No account mode, selected family, or credential file should be rewritten.
2. Supply the account source with the real built-in configuration source and current settings/identity obtained through official services. `createAccountProviderConfigSource(options)` constructs `AccountProviderService`, whose `read()`/`refresh(reason)` produces its authoritative snapshot. Its connection resolver checks current account identity/settings and does not take a menu label as entitlement. [Account source implementation](https://github.com/zai-org/ZCode/blob/aac4755666d09fdcd70272fcf063c077a639015f/packages/services/src/model-provider/accountProviderConnectionResolver.ts).
3. Use `createCodingPlanFamilyAvailabilityResolver({apiClient, credentialService})` for genuine availability. The Start Plan path loads account authorization internally, queries the real balance/plan service, validates an active plan, and derives permitted models/effective time from the server response. Missing authentication, unavailable entitlement, pending activation and unknown/network results remain distinct. It cannot be replaced by invented `entitled: true` or configured model names. [Start Plan availability](https://github.com/zai-org/ZCode/blob/aac4755666d09fdcd70272fcf063c077a639015f/packages/services/src/model-provider/codingPlanProviderAvailability.ts).
4. For a genuine runtime request, the official `AccountProviderRequestAuthService.resolveCurrent(input)` resolves current access and, for Start Plan, obtains the current `zcodeJwtToken` through `OAuthCredentialRepo.loadTokenSet`. The official agent service synchronizes the real snapshot using `provider/updateAccountConfig`, checks `receivedRevision`, and resolves request auth before responding to the exact provider-headers callback. The material must remain inside the trusted host's private transport; success requires actual material and the relevant security policy. A caller-supplied `headersApplied: true` is insufficient. [Request authentication](https://github.com/zai-org/ZCode/blob/aac4755666d09fdcd70272fcf063c077a639015f/packages/services/src/model-provider/accountProviderRequestAuthService.ts), [agent synchronization and callback](https://github.com/zai-org/ZCode/blob/aac4755666d09fdcd70272fcf063c077a639015f/packages/services/src/zcode-agent/zcodeAgentService.ts).

There are concrete reasons not to execute a stock `createLocalServices()` as a read-only probe. It initializes process environment, may create an app CA, constructs settings migrations, and starts other service/background paths. The credential reader may back up a corrupt store; the OAuth repository may clear a corrupt session. Official implementations are not guaranteed to have zero writes on their error paths. A future narrow host must fail closed on those writes/recovery actions and contain any secret material in private memory, rather than copy an existing store. [Credential reader](https://github.com/zai-org/ZCode/blob/aac4755666d09fdcd70272fcf063c077a639015f/packages/services/src/credential/credentialService.ts), [OAuth repository](https://github.com/zai-org/ZCode/blob/aac4755666d09fdcd70272fcf063c077a639015f/packages/services/src/oauth/repo/oauthCredentialRepo.ts).

The default `createNodeApiClient` also calls `buildZCodeSourceHeaders()`, which fixes `sourceTitle` to `electron` and does not expose a source-title option. A custom external host must not reuse that default and present itself as the official desktop. Whether a truthful external-client transport is accepted by the business service remains unverified. The public repository's request-security edition also has its own policy implementation; its presence is not permission to replace or disable the installed runtime's security behavior. [Source headers](https://github.com/zai-org/ZCode/blob/aac4755666d09fdcd70272fcf063c077a639015f/packages/services/src/providers/sourceHeaders.ts), [public edition policy](https://github.com/zai-org/ZCode/blob/aac4755666d09fdcd70272fcf063c077a639015f/packages/shared/src/request-security-edition/verification-policy.ts).

Consequently, there is no established fundamental Electron-only credential barrier, but there is also no verified ready-made external SDK route in the installed artifacts. The next discriminating work is an isolated, version-pinned source build and a bounded **zero-model** genuine service query with truthful client identity and denied mutation paths. That work has not happened here. No desktop IPC injection, security-policy substitution, guessed authorization or direct credential extraction is justified by these findings.

## GPT API alternative and the separate experimental observation

The OpenAI Responses API response schema includes `id`, `status`, `model` and `usage`; the returned `model` is described as the model used to generate that response. A real authenticated response, bound to its request/response ID, offers stronger execution identity evidence than a configured Codex thread model. It still does not disclose arbitrary internal hardware/model implementation beyond the service's reported identity. [Official OpenAI response schema](https://developers.openai.com/api/reference/python/resources/responses/methods/create).

`OPENAI_API_KEY_present=false` in this process means this check did not find a ready environment credential for that alternative. Credential validity, model access and billing would remain unknown even if presence were true. No key was created, API request sent, route switched or existing frozen model route changed.

For root's separately authorized one-turn experiment, the local Codex 0.160.0 schema allows `thread/start` with `ephemeral:true`, `sandbox:"read-only"`, `approvalPolicy:"never"`, `dynamicTools:[]` and `experimentalRawEvents:true`. The raw-events flag explicitly says internal use only. `turn/start` requires `threadId` and `input:[{type:"text",text:"<fixed inline input>",text_elements:[]}]`; its read-only override is `sandboxPolicy:{type:"readOnly",networkAccess:false}`. There is no `toolAllowlist` parameter; an empty dynamic-tools list does not disable built-in tools. Unsupported tool/approval callbacks must fail honestly and terminate the experiment if encountered. `usageMetadata.metadata` has an arbitrary-JSON schema, not a guaranteed model field. Only actually observed execution fields bound to the genuine response/thread/turn qualify as experimental execution evidence; their absence remains unknown. This experiment must not relax the production metadata transport's prohibition on model methods or be described as guaranteed SDK support.
