# Native GPT scope: narrow source finding

The requirement can be expressed as preventing model-triggered filesystem access and arbitrary host execution; pure clock or plan tools need not be removed. The absence of a public all-tools allowlist is therefore insufficient to conclude that native scope enforcement is impossible. Version-pinned source supports a promising public configuration combination. It has **not** been applied or validated as a production boundary, so `scope_enforced=false` remains correct.

The installed `ThreadStartParams` and `TurnStartParams` schemas explicitly define `environments=[]` as disabling environment access. `core/src/environment_selection.rs` keeps that selection empty. `core/src/tools/spec_plan.rs` then omits shell execution and stdin tools when there is no environment (1081–1088), omits `apply_patch` (1269), and omits `view_image` (1283). Clock and plan tools can remain. This is an actual native tool selection restriction, rather than using a working directory as an OS sandbox.

Additional tool sources need independent controls. The fixed official [app-server extension set](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/app-server/src/extensions.rs#L70) installs MCP/plugins, memories, web search, image generation, and skills alongside control/context services. `features.plugins=false` reaches `PluginsConfigInput` and returns an empty plugin load outcome. Every configured MCP server must independently have effective `enabled=false`; `features.apps=false` alone does not disable user MCP servers. An empty `mcp_servers={}` table does not remove existing tables because configuration merging is recursive. These merge and server checks were independently traced by the storage lane.

The skill tool source returns no tools when cloud skills are disabled and there are no executor roots. The canonical public key is `cloud.skills.enabled=false`; `cloud_skill=false` is not the correct key. Empty environments prevent executor roots. Memory read tools require the `MemoryTool` feature, whose current canonical key is `features.memories`, and `memories.use_memories`; disabling these removes that read path. Image generation and web search have separate feature/mode filters in the native tool plan. User/global instructions loaded by the CLI are distinct from model-selected filesystem tools and must remain preserved.

Code Mode needs canonical settings. In this tag, `js_repl` and `js_repl_tools_only` are legacy no-ops. `model_info.tool_mode` can override ordinary feature-based tool selection, so disabling `features.code_mode` alone is not a complete proof. However, the [thread manager](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/core/src/thread_manager.rs#L532) chooses `DisabledCodeModeSessionProvider` when both the compiled CodeModeHost feature and compiled `code_mode.disable_in_process_fallback` value are false. The [disabled provider](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/code-mode/src/remote_session.rs#L80) rejects both availability and session creation. The public schema supports a typed Code Mode host table. The probe therefore sets its members explicitly with `-c features.code_mode_host.enabled=false` and `-c features.code_mode_host.disable_in_process_fallback=false`, alongside `features.code_mode=false` and `features.code_mode_only=false`, and requires both actual effective members to be boolean false.

The compiled `code_mode.disable_in_process_fallback` field is not an independently supported top-level TOML override. It is populated from the typed `features.code_mode_host` configuration. Setting that typed-table member true would select a process host in this constructor. A bare `features.code_mode_host=false` does not establish its other member is false: structured feature merging can retain existing table members while changing only `enabled`. The earlier default-value inference was therefore withdrawn. Both typed members must be checked directly.

A zero-model validation plan is available: use only the pinned native local app-server entry, per-process configuration overrides, and an ephemeral thread with empty environments and dynamic tools. Keep existing auth opaque, all user rules and managed requirements intact, and the existing stricter read-only/network-disabled/approval-never policies. Read effective configuration through official RPC privately; export only whether the canonical flags, disabled MCP server set, plugin state, and empty environment selection match. Reject unknown, unresolvable, or managed-required conflicting states before any model call. Validate that no RPC path can attach an environment, refresh tool permissions, install a plugin, supply dynamic tools, or authorize a server callback. Do not use a model call merely to check these fields.

The candidate public controls are `features.shell_tool=false`, `features.view_image=false`, `features.code_mode=false`, `features.code_mode_only=false`, both typed Code Mode host members above, disabled multi-agent/app/plugin/tool-suggestion features, `features.memories=false`, `memories.use_memories=false`, `cloud.skills.enabled=false`, `features.image_generation=false`, `web_search="disabled"`, and explicit disabled configured MCP servers. For background host execution, `features.hooks=false` is the canonical hook feature; `codex_hooks` is not its current canonical key and `plugin_hooks` is a removed no-op. The legacy `notify` array needs a separate check: `notify=[]` replaces an array, but must be confirmed in the effective configuration. Controls should be checked by canonical schema and implementation, rather than guessing deprecated key names.

The CLI [override parser](https://github.com/openai/codex/blob/rust-v0.160.0/codex-rs/config/src/overrides.rs#L20) splits a dotted path literally and does not parse quoted path segments. Consequently `mcp_servers."name".enabled=false` creates an unintended literal quoted key. To disable the privately enumerated configured servers, the corrected probe uses one top-level `mcp_servers` inline TOML table containing each exact quoted key and only `{enabled=false}`. Recursive merging retains transport/auth configuration inside the CLI without copying those values into argv. The actual effective key set must exactly equal the baseline set, and every returned member must explicitly be disabled. The original failed zero-model metadata reports are preserved.

One remaining consistency question is live configuration refresh: `Session::refresh_runtime_config_inner` refreshes the MCP server map. A startup enumeration of disabled server names must not silently permit a later newly configured server. A future runtime needs a stable effective tool boundary or a verified rejection/termination policy for such changes, including native internal steps. This source review did not run a CLI configuration probe, enumerate HOME, execute a tool, change user settings, build a binary, or submit any model request. It does not prove that the proposed public combination is impossible; it establishes the controls that can be used and the runtime checks still needed before promotion.

The public-source cache and hashes are recorded in `.tools/gpt-scope-source/source-manifest.json`; existing tool-plan/config sources are in `.tools/gpt-response-identity-source/source-manifest.json`. The separate successful SSE model-identity observation does not validate this new scope policy.

The subsequent actual zero-model probe completed the effective-configuration and owned empty-environment checks: all 21 required returned-value controls and the exact disabled MCP set passed. Results and preserved failures are in `gpt-scope-zero-model.md` and `gpt-scope-zero-model-verified.json`. This upgrades the proposal to verified metadata preconditions, while production execution scope and the complete refresh lifetime remain unqualified.
